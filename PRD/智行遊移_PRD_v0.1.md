## 1. 產品定位與目標

對外定位：**AI 情境推薦 × 步數遊戲化的雙引擎成長模式**。

產品整合於 yoxi 使用旅程，讓使用者從「我要叫車，所以打開 yoxi」逐步轉為「今天怎麼移動？先問 yoxi」。品牌主張為「走得到就走，需要時 yoxi 接你」。

- 步數遊戲化：提供每日開啟、領點、持續參與、組隊與邀請的理由。
- AI 情境推薦：提供每日移動決策價值，服務不參與步數遊戲的使用者，並在適當情境導向 yoxi；主要對應啟動與轉換。
- 展示目標：團隊能完整操作步數、領獎、共享團隊及邀請流程，理解規則並辨識介面問題。AI 推薦仍屬長期雙引擎定位，首版不開發。真實留存、獲客、GMV 與轉換增量屬未來商業假說，本版無法驗證。

## 2. 目標使用者與需求

已確認：首批目標族群為上有老、下有小的上班族；本次實際體驗者為團隊成員。

以下需求屬待驗證設計假設：工作與家庭行程壓縮決策時間；接送孩子、陪長輩出門時更在意準時與少走路；一般通勤或短程外出時仍可能偏好省錢與步行。

設計原則：少量輸入、清楚理由、可修改偏好；不得僅依步數認定疲勞，也不得因年齡或家庭角色直接推定健康狀態。步數獎勵不得壓過使用者明確的時間及行動限制。

## 3. 入口與展示範圍

已確認的目標旅程：yoxi 現有首頁 → 步行移動 GIF 入口 → 點擊進入智行遊移 RWD web app。

展示版依使用者提供的 yoxi 首頁截圖製作可點擊示意：上方保留地圖區及既有功能圖示，下方保留「嘿！今天要去哪？」與目的地輸入區；在下方表單上緣加入可點擊的步行動態入口及「智行遊移」文字標籤，進入 RWD web app，避免覆蓋原有上下車欄位。GIF 暫用動態素材，最終品牌素材可替換；停用動態時提供靜態圖及同樣可點擊的文字入口。示意畫面不宣稱已改動正式 yoxi App。**2026-10-04 修訂（FSD-08A-2）**：示意頁裁掉手機狀態列、問候語改為「嗨，今天要去哪？」，入口改為 yoxi 漢堡選單正下方的 yoi 魷魚動態按鈕（漂浮、脈動光環、偶爾搖擺、NEW 標籤，不放可見文字），角落標示「示意畫面」；開網址先看到示意頁，主畫面選單與登入頁可返回。

首版必含：個人步數與領點、全部領取、補領、乘車加成、每週七日全勤、跨裝置共享團隊、寶箱、邀請、站內提醒、獎勵紀錄。AI 推薦的輸入介面、推薦卡、規則模擬、模型串接及回饋流程皆不列入首版。

首版步數、行程與 Points 使用模擬資料。位置、天氣及移動偏好待 AI 功能規劃定案後再設計，首版不為推薦額外建立相關流程。叫車入口終點為叫車確認示意，無真實訂單、支付或入帳。

已確認：團隊成員使用不同裝置進入同一展示環境，必須能看到彼此的模擬步數、加成與團隊進度。資料內容為模擬，跨裝置共享為實際功能。以共享資料服務保存展示身分、步數、團隊、領獎與邀請狀態，本機儲存僅作快取。

### 3.1 D06 展示整合方式【展示流程已確認；技術選型為首選建議】

1. 六名團隊成員從同一展示網址進入，以各自的帳號與密碼登入。每個帳號綁定固定身分 ID；不以暱稱識別，也不提供公開註冊入口。管理者帳號屬其中一名成員，具有額外管理權限。六個正式展示信箱由產品負責人後續提供；開發與測試可先使用專用測試帳號，展示前再核對六個帳號的登入與身分綁定。
2. 第一畫面依提供的 yoxi 首頁截圖建立示意，在叫車表單上緣加入暫用步行動態素材與「智行遊移」文字入口。點擊後進入實際可操作的 RWD web app，並提供返回首頁示意的操作。
3. A 建立招募並分享隊伍邀請碼，B 在自己的手機輸入邀請碼；兩人加入後成團。A 更新自己的模擬步數，B 的隊伍畫面自動更新，反之亦然。
4. 步數、行程及獎勵採模擬資料，叫車按鈕導向展示畫面。AI 推薦不開發；展示身分與共享服務不等於正式 yoxi 會員串接。
5. 首選 Firebase Hosting（展示網址）、Firebase Authentication 電子郵件／密碼登入、Cloud Firestore（共享資料及即時訂閱），使用獨立展示專案，不與其他產品資料混用。原始碼按積木拆分，前端交付仍可打包為單一 HTML。此處為技術建議，實際專案與部署尚未執行。
6. 若有正式 yoxi App 的修改與測試環境，之後可將 GIF 入口改接相同 web app 網址；目前首頁示意不宣稱已完成正式 App 整合。首頁截圖已提供，最終 GIF 素材仍可後續替換。

### 3.2 六人展示與雲端選型

展示目標為 9 月 30 日讓六名成員各自在手機開啟同一網址，以獨立帳號看到共享團隊步數。正式信箱可後補，展示前需完成六個帳號建立與登入驗證、可從六人未組團狀態建立至少一個兩人隊伍、管理者帳號、跨裝置同步與結算情境資料。更換測試信箱時以固定身分 ID 維持原資料歸屬，不以顯示名稱或信箱文字作資料主鍵。

Google AI Pro 訂閱不等於 Firebase 專案或帳單已自動建立。Google 官方目前列有每月 US$10 Google Cloud 抵用額及 Firebase Studio 使用權，但抵用額資格、綁定方式與剩餘額度需在帳號中確認。六人展示優先使用 Firebase 的 Spark 免費方案；若所選實作確實需要付費服務，再另列需要開通的服務與預估費用，由產品負責人決定。Firebase 專案建立、計費設定與部署屬展示環境執行工作，不由這份 PRD 自動完成。

已確認：Firebase 專案管理權限暫由產品負責人兼主要開發者持有。其他團隊成員使用展示帳號進入 web app，不因此取得 Firebase 專案管理權限。開發測試帳號與正式展示帳號分開管理；密碼不寫入 PRD 或原始碼。

帳密由受管理的身分服務處理，不將密碼寫入 HTML、原始碼或共享資料。展示成員僅能編輯自己的模擬步數與行程，能讀取同隊成員的步數；管理者能設定共用情境時間、準備展示資料及重設指定展示場次（首版的展示資料由重設場次後各成員自行操作產生；管理者代填步數列為後續版本，2026-10-03 FSD-02C）。獎勵、隊伍與結算等跨成員狀態由共享端保存，不能只依各手機的本機資料。

展示版不開發自助忘記密碼流程；由產品負責人在身分服務中協助重設，不透過應用介面顯示或保存密碼。未來正式版密碼控管沿用當時 yoxi 的既有方式，本版不預設其細節。

同步採資料變更後即時推送／訂閱，不刻意等待五秒或以五秒輪詢作為預設。先前五秒僅為建議驗收容許值，並非技術下限。

已接受的同步目標（待實測）：兩端頁面均在前景、正常連線、共享連線已建立時，從 A 提交步數更新至 B 完成畫面更新，95% 操作在一秒內完成。服務端保存到 B 顯示的傳播延遲另記錄，避免忽略上傳耗時。每次測試記錄網路、裝置、操作樣本數與延遲分布；開發前不宣稱已達此目標或保證所有情況一秒。

A 操作後立即顯示「同步中」，共享服務確認後才顯示「已同步」；B 接收後更新數字及最後同步時間。斷線或儲存失敗明確標示未同步，重連後重新讀取共同狀態。初次載入、背景喚醒及斷線重連另外驗收，不與正常連線的更新延遲混計。

## 4. AI 情境推薦最小流程【後續版本備案，首版不開發】

以下保留先前提案供團隊後續討論，尚未定案，不構成首版開發任務或驗收要求。

### 4.1 操作流程

1. 進入首頁即看到「今天怎麼移動？」與獨立入口，不以參與步數或加入團隊為前提。
2. 選擇目的：上班／回家、接送孩子、陪長輩出門、附近辦事。目的僅協助預填，使用者可修改。
3. 確認目的地及時間需求：「現在出發」或「希望幾點到」。展示版使用預設地點及可選時間。
4. 提供一列可選條件：「想省錢」「趕時間」「少走一點」「帶孩子」「陪長輩」「攜帶物品」。不要求每個人逐項填寫；位置、天氣、步數及移動偏好以模擬資料預填並允許調整。
5. 顯示一個主要建議及最多一個可行替代方案。每個方案顯示交通方式、模擬預估時間／費用、簡短理由；時間若含候車與步行需清楚表示。
6. 使用者選擇「採用步行建議」「查看 yoxi 叫車」或「調整條件」。步行顯示路程摘要；叫車顯示上下車點、模擬費用及可用獎勵，等待使用者確認。
7. 收集「有幫助／不適合」回饋；後者可選時間、費用、步行量等原因。展示版保存回饋，但不宣稱模型已自動學習。

### 4.2 第一版展示情境

| 情境 | 模擬條件 | 建議體驗 |
|---|---|---|
| 午休附近辦事 | 晴天、短距離、時間足夠、未要求少走 | 優先步行，附預估步行時間；步數進度作次要資訊 |
| 下班接孩子 | 下雨、有抵達期限 | 比較含候車的叫車總時間與步行時間；符合條件時推薦 yoxi，不保證準時 |
| 陪長輩出門 | 使用者主動選擇少走路 | 優先較少步行的方案，顯示上車位置；不承諾未驗證的無障礙車型服務 |
| 下班回家 | 使用者選擇想休息 | 顯示 yoxi 方案及理由；步數高只能作背景資訊，不等同疲勞判定 |

### 4.3 判斷與異常狀態

先考慮明確行動限制及抵達時間，再考慮天氣、距離、費用偏好，最後才提示步數進度與獎勵。不為推銷叫車而隱藏合適的步行方案。

缺目的地時要求選擇；缺天氣／位置時標示缺漏並允许手動選擇；沒有能符合抵達期限的方案時如實提示。展示版第一輪比較步行與 yoxi 兩類方案；大眾運輸整合暫列後續建議，待審核。

## 5. 個人任務與獎勵規則

### 5.1 已確認規則

- 原始步數與任務有效步數分開呈現。當日完成至少一趟 yoxi 搭乘，即適用當日原始步數 ×1.5；每日最多加乘一次。有效步數取整數部分。
- 展示版每位成員每個任務日的模擬原始步數只可持平或增加，不允許下修；共享端須拒絕低於已保存數值的更新，包括另一裝置送出的舊值。
- 每次增加模擬原始步數，保存新增量、步數發生時間與同步時間，供團隊依入隊／暫停時段判定貢獻；今日一般操作的發生時間預設為共用情境當下。補同步昨日資料時，成員不選擇時間，系統將增加的步數記為昨日 23:59:59（Asia/Taipei）發生（D14，2026-10-01 修訂）；補同步仍須在 D+1 日 24:00 前完成。同步時間不得代替發生時間；同值重送不新增步數片段。
- 每日點數、連續七日與團隊貢獻均採加成後步數。取消或未完成行程不代表已搭乘；跨日行程以完成日歸屬，沿用前版定義。
- 團隊達標時點另依乘車完成時間判定：完成當日首趟合資格搭乘時，加成增加的團隊貢獻才在該完成時刻生效；搭乘前已發生的步數仍可作為加成基數，但不得把「因加成才達標」的時點倒推至搭乘前。搭乘後新發生的合資格步數依已取得的當日加成計入。個人每日有效步數及領點門檻仍按當日總量計算。
- 本項加成不新增信用卡等限制；推薦邀請首乘的既有條件另行適用，不與加成混用。
- 2,000／4,000／6,000 有效步數各新增 1 點，累計最多 3 點。里程碑自上而下顯示「累計 1／2／3 點」，各按鈕清楚標示本次領取 1 點。
- 達標僅解鎖；進入 web app 主動領取後才增加模擬餘額。提供逐點及「全部領取」，後者只領取該任務日已解鎖且未領的部分。
- 逐點必須依第 1→2→3 點順序領取；即使已達 6,000 步，未領前一點時也不能直接領後一點。「全部領取」按此順序完成該日所有已解鎖且未領點數。
- 未達標為暗色不可點擊，達標未領為亮色可領取，完成後顯示已領取。
- 任務日 D 的點數可於 D 當日領取，最晚至 D+1 日 24:00 前補領。等同 D+2 日 00:00 起不可領取；時區沿用 Asia/Taipei。
- 每日最多 3 點以任務歸屬日計算；昨日與今日分區，補領昨日不占今日額度。點數紀錄保留任務日及實際領取時間。
- 次日才同步到昨日步數，允許補算昨日達標與點數資格。單純「補領」不改步數；「補同步」可以更新昨日步數並重算相關資格。

### 5.2 每週七日全勤【週期已確認】

個人與團隊統一以 Asia/Taipei 每週一 00:00 開始、週日 24:00 結束（下週一 00:00 不屬於上週）。個人每個曆日達 6,000 有效步數即為達標日；該週七日全部達標取得乘車獎勵券資格，達標紀錄與點數領取分開。全勤只看七日有效步數，與當日點數是否領取無關（FSD-04B，2026-10-05 修訂）；得券提示在券入帳後顯示。

每週一開始新一輪，與領券時間無關；不採任意連續七日滾動累計。例如週三至下週二皆達標，不能跨週合併成一輪全勤。週中開始參加者仍可每日領點，但未符合該週全部七日條件就無全勤券。UI 應使用「本週已達標 X／7 天」與週一至週日格子。

缺資料且仍在補同步期限內的日期標示待同步；期限後未達標則該週無法全勤，但其他日期仍可領點。週日資料可以在週一 24:00 前補同步，必要時补發上一週的全勤資格；新週同時獨立累計。以使用者 ID＋活動週 ID 防止同週重複解鎖。

已確認券面額 NT$50、效期自券成功入帳時的**共用情境時間**起算 30 天、最低車資 NT$150（含）方可使用，介面明示到期時間；真實伺服端時間僅留作稽核，不用來計算展示券效期。同一場次情境時間只可向前推進；已入帳券的起算與到期時間固定，不因提示關閉、重試或場次內時間推進而重設。符合當週全勤條件（七日有效步數皆達 6,000）即自動發券，不另設領券按鈕，也不要求領取任何一天的點數（FSD-04B，2026-10-05 修訂；原「週日第三點」條件取消）。

已確認互動（FSD-04B 修訂）：本週七日達標並經伺服器確認後即發券，系統顯示恭喜獲得乘車獎勵券及鼓勵文字（有其他視窗開著時延到關閉後）；同一使用者同一活動週只發一張券，重點、刷新或跨裝置重試不能重複發券。

## 6. 團隊、寶箱與邀請

### 6.1 團隊

已確認：至少兩人才能成團，最多五人；每週固定 300,000 有效步數，不按人數或成立日調降；週期與個人任務相同。團隊顯示成員各自的今日原始／有效步數、本週貢獻、加成來源、總進度與同步狀態。

已確認：隊伍、現有成員與隊長跨週持續保留，不因週一開始新週自動解散或重新成團；只有各週貢獻、目標與獎勵資格分週計算。成員異動依下列規則；已成團後只剩一人的隊伍跨週仍維持暫停，補足兩人才恢復。無成員時依既有規則封存；是否提供隊長主動解散操作仍待決。

### 6.1.1 D04 成員加入、更換與退團【已核定】

- 一人為招募中；第二人加入時正式成團。只計成團後且本人在隊期間產生的步數片段，再套用該日乘車係數；補同步以步數發生時間判定片段歸屬，乘車加成造成的增量以搭乘完成時間作為團隊生效時點，不回溯改寫搭乘前的達標時點。
- 一人同時只能有一個未成團的招募隊伍；要加入他隊，須先取消自己的未成團招募。取消招募不占用當週正式隊伍資格。
- 每人每個活動週只能貢獻給一個正式團隊。退團可立即生效，但當週不得再加入或重回任何正式隊伍，下週一才能重新組隊；未曾正式成團的招募不占用當週資格。
- 退團前已產生的有效貢獻保留，標示歷史成員貢獻；退團後不再增加。其後補同步仍可更新退團前的合資格片段，不能把同一片段移到新隊伍。
- 未達標團隊可補入當週尚未參加正式隊伍的人；新成員僅計入加入後步數，目標仍為 300,000。
- 退團後剩一人則暫停任務及新增貢獻；保留已累積數值，补足兩人後恢復，暫停期間的步數不回補團隊。暫停不影響個人每日點數或全勤。
- 團隊首次合資格達標時記錄獎勵名單；達標時已退出者無獎，達標後退出者保留已取得資格；達標後加入者不分享該週寶箱。補同步可依歷史時間新增合資格成員，但已授予的寶箱資格不撤銷，詳 6.2；名單採保留既有資格並補充，不因歷史重算覆寫。
- 退團僅能由成員本人發起；隊長不得主動將其他成員移出隊伍。隊長本人退團及主動更換隊長詳下一節；沒有成員時封存隊伍並保留結算紀錄。
- 退團確認畫面說明「已貢獻保留、當週不能換隊、未取得的寶箱資格可能失去」。

### 6.1.2 隊長接任與更換【功能已確認】

- 隊長退出，由最早加入且仍在隊伍內的成員自動接任。
- 系統內提供「更換隊長」操作，後續可再次更換。
- 已核定操作細節：現任隊長在團隊管理選擇現有成員，確認後轉讓；原隊長保留一般成員身分。僅現任隊長可主動轉讓，不能指派已退團者。
- 更換隊長不重設步數、週期或獎勵資格，並向所有成員同步最新隊長。相同加入時間可依穩定成員 ID 決定接任順序。
- 退團與轉讓同時發生時，共享服務需確保最終只有一位有效隊長，不產生重複或無效隊長。

### 6.2 寶箱

展示基線：達標當下每位合資格成員各得一箱，預先抽取並保存；每人每週至多一箱。已核定領獎方式：開箱時將固定結果入帳，動畫僅揭示結果；未開寶箱跨週保留，展示版不設開箱期限。跳過或中斷動畫不影響已完成入帳，重開不再發點。

| 獎項 | 內容 | 暫定機率 |

跨週補同步已確認（D05）：週日貢獻可在週一 24:00 前補回上一週；新週獨立累計，上一週保留待結算。補同步後首次達標，以歷史貢獻還原達標時間及當時成員資格，僅生成一次上一週獎勵。需保存步數片段的發生時間、同步時間、會員異動歷史與所屬活動週，不可用週一當下名單覆蓋上週資格。
